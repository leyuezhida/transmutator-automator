嬗变台：大变 v1.0.1

自动避开堆叠上限不同的候选。

---

### 问题

v0.1.0 只避开"会立即让数量变多"的候选（`新上限 > 当前上限`），理由是"避免膨胀"。**这个规则是错的。**

上限变小同样有隐患 —— 它只是**把爆炸延后**：

```
泥土(64) → 雪球(16)    得到 1 个雪球，数量没变，看着安全
雪球(16) → 木棍(64)    得到 4 个木棍    ← 突然膨胀
```

第一次转换时数量看起来没问题，**下一次转换就炸了**。物品在上限不同的空间里来回跳，每一次跳都是一次权重扰动。

用服务端公式验证 7 种组合后确认了这一点。举例：槽位上限 64、候选为 `[16, 64, 16]` 时，旧规则会选那个 16 —— 正是本版要避开的。

### 改动

**只点堆叠上限与当前物品相同的候选**，只要对不上就跳过。

三个候选都对不上时，**选上限数值最接近的那个**，而不是像以前那样点第一个。数量换算是 `原数量 × 新上限 / 原上限`，上限越接近倍数越接近 1，扰动越小。卡着不动等于完全刷不到东西，所以退让必须发生，但退让要退得最省。

### 验证方式

每 20 次嬗变会打一条日志，能直接看出避让有没有生效：

```
堆叠上限：槽位=64 候选=[16, 16, 64] 实选第 3 个
```

### ⚠️ 有一个无法规避的情况

**槽位里放上限为 1 的物品（钻石、煤等）**，而三个候选都是上限 16（雪球、末影珍珠等）时：

```
1 × 16 ÷ 1 = 16 个
```

这是服务端公式算出来的结果，客户端模组**无法避免**。解决办法很简单：**槽位里放上限为 64 的普通物品**（泥土、木棍、石头之类）。

### 顺带修复

改版本号时发现 jar 里的 `version` 字段被污染成
`1.0.1XXXX escapes, because Groovy reads...`。

原因是 `mods.toml` 的注释里写了 Unicode 转义前缀，而 `expand()` 在处理模板时**也会解析它**，把后面的注释行拼进了上一行的值。这个问题从 v0.1.0 就存在，只是版本号没变所以看不出来。
